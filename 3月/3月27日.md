## Swagger注释

**使用$Swagger$注释可以生成一个交互式文档页面，包含**

- $API$分组展示

- 每个$API$的详细说明

- 参数说明和示例

- 响应示例

- 可直接测试$API$的界面

### 包级别的注释

```go
// ResignerLogList 注册日志相关路由
```

这是方法的简单描述，$Swagger$ 会将它用作 $API$ 的简短介绍。

### Swagger主注释

```go
// @Summary 注册日志路由
// @Description 注册日志列表和详情查询的路由
// @Tags 日志管理
```

- $@Summary: API$ 的简要描述，显示在 $API$ 列表中
- $@Description: API$ 的详细描述
- $@Tags: API$ 所属的标签，用于分组显示

### 输入输出定义 

```go
// @Accept json
// @Produce json
```

- $@$$Accept:$ 定义 $API$ 接受的请求数据类型
- $@Produce$: 定义 $API$ 返回的数据类型

### 参数定义

```go
// @Param op_log_id query string false "操作日志ID"
```

$@Param:$ 定义 $API$ 参数

- 格式: `@Param 参数名 参数位置 参数类型 是否必须 "参数描述"`
- 参数位置: $query$($URL$ 参数), $path$(路径参数), $body$(请求体)等
- 是否必须: $true$ 或 $false$

### 响应定义

```go
// @Success 200 {object} gin.H "成功返回日志列表"
// @Failure 400 {object} gin.H "参数解析失败"
// @Failure 500 {object} gin.H "查询错误"
```

- $@Success:$ 定义成功响应
  - 格式: `@Success 状态码 {响应类型} "描述"`
- $@Failure:$ 定义错误响应

### 路由定义

```go
// @Router /Log-list/log [get]
```

定义 $API$ 的具体路由和方法

## $JSON$的序列化和反序列化

**序列化**，也可以说是**反解析**。指的是**将对象的状态信息转换为可以存储或传输的形式的过程**。

而**反序列化**，对应的可以说是**解析**。指的就是序列化的逆过程。

**结构体中每个字段首字母必须是大写，这样各个字段才是可被访问的，才能顺利完成序列化。反序列化也同理**

## Swagger文档生成

好像是在使用预定义的匿名结构体类型如$gin.H$时会报错

要使用有具体类型的结构$web_model.JsonResponse$就可以避免

其中对于$web_model.JsonResponse$，需要在$web_model$中

定义$type\ \ JsonResponse\ \  map[string]interface\{\}$

而$H$是$type\ \ H\ \ map[string]any$

-------------

**?? 也就是说如果要生成$swagger$文档就要使用有具体类型的方法而不能用匿名方法吗 ??**

**不一定非要具体类型**，但匿名方法需要特殊处理！就像：

- **具体类型** = 有身份证的公民（$Swagger$一眼能识别）
- **匿名方法** = 戴口罩的游客（需要额外说明身份）

**优势**

- $Swagger$能直接解析类型定义
- 自动生成响应模型文档
- 代码可维护性强

可以使用匿名方法访问，但是要用一定的格式去完整注释
